# 业务资料夹与做账规则

## 凭证草稿的品目类型（2026-11-23，BUG-06）

- 生成与改记入期必须使用所选公司来源的品目表：工作区将完整代际明细和来源目录 `成本开票状态.json` 成对传入，CLI 的根明细读取其相邻状态。缺状态保留旧档案兼容，损坏/未来版本不得降级为空表；生成前后复核状态原字节与目录身份，变化则保留原审核表并要求重新生成，不承诺外部编辑器跨进程事务。
- 原票明细先按标准名称链解析类型，再合并库存品类。显式服务/费用/资产不得进入库存购入、历史数量更正、销项出库和销售成本；原名称、金额与发票依据必须保留。非货物只使用精确销售方+原名/标准名的已确认可用非库存科目或对应习惯；缺少、歧义、不可用科目或库存冲突时单列金额、空编码并列入待补，由同一 validator 阻断审核通过和整月导出，不能猜费用科目或回退库存。
- 零税额票不生成零金额税额行，保持原票金额及正金额校验。服务销项仍走既有收入分录，只有货物数量结转库存；这项保护不表示完整服务科目引擎、服务毛利成本入账或真实账套验收已完成。

## 成本 V2 显式库存对照与期初（2026-11-21）

- 公司根目录 `库存科目对照.json` 是人工确认的品名→现有末级库存科目、期初和完整读回月份声明，不是新增账套科目或修改账本；绑定当前科目表语义，变更需重新预览确认。CLI/草稿、进销存和 V2 共用 `bank.stock_mapping`，别名在预览中展开，未配置保留旧算法。已确认映射与已保存做账习惯/映射规则冲突须拒绝，不静默覆盖。
- 明确期初（包括明确零期初）成为发票滚动起点，早前发票不重复计入；草稿从期初到首月的账面结存需要逐月完整声明及实际读回。确认期初不得再用历史购销总量自动纠正；缺覆盖、重复库存行、数量方向不明或单位冲突拒绝建立可信账面余额。仍按原 `cost_of_sales` 品类月末一次加权，不按规格开库存。
- 月末账面核对只读，非月末/无基线/未映射/来源不完整时明确待核对，不把缺失当零；差额是账面减发票滚动，不自动补凭证或执行账套操作。库存设置保存按成本锁→草稿锁顺序重核来源、原子写与读回；CLI/外部编辑器跨进程事务不在保证内，真实操作仍须当回合明确授权。

## WS-02 候选目录与 WS-05 工资确认（2026-11-19）

- 检测表可选择同类多个安全直接子目录；跨类型歧义仍不猜。标准名优先的旧自动检测保持兼容；用户也可显式选标准目录再补建。所选映射与全部候选身份进入同一计划，未选或目录变化不得登记，不移动或合并候选。
- 工资只读取明确表头和表内期间的 `.xlsx/.xlsm` 仅值表，不从文件名猜月、不执行公式、不按费率补扣款。空白不是零，姓名重复/金额不平/合计行不符拒绝整个文件。多源同月必须明确选一个，不能自动累计。
- 工资确认写 `申报数据.json.工资明细`，与社保共用 SHA、写锁及 2 MiB 文件上限，保留其他键；坏工资不能被社保操作当空覆盖。候选绑定公司/映射/目录/源文件 SHA，保存重新解析而非信任页面人员行；生成前原表不一致须重新确认。默认脱敏，完整人员值不得出现在公共错误或公开夹具。
- 只按用户明确费用/成本科目路径计提应发工资，缺科目进入待补并阻断审核；已读回入账月跳过。不从工资表生成付款、个税缴纳或再次社保个人代扣，不执行账套操作。工资原表确认不代表税务政策复核。进程内锁不承诺外部编辑器/CLI 跨进程事务，真实 Windows/网络盘语义另验。

## 做账（bookkeeping）规则

- 做账数据真值全部在公司资料夹 `凭证/` 下，包括 `账套配置.json`、`科目表.json`、`辅助核算档案.json`、`科目映射.json`、`凭证生成状态.json`、`批次/` 和 `日志/`；真实业务数据不得进入仓库。仓库只保存结构性 `docs/jierui` facts/selector、确定性生成代码和随包 runner。
- `凭证生成状态.json` 只允许 InvoiceHub 后端通过严格仓储、跨进程写锁和单调 revision/CAS 写入；合法 JSON 但 schema 错误、未来版本或结构损坏时必须保留原文件、写诊断并停止后续写入，不得把异常状态当空对象覆盖。
- v1 状态必须先 preview，再以源文件 SHA256 和 `confirm=true` 显式迁移到 schema v2；禁止启动时自动迁移。迁移不得静默丢弃已审批、已导出、已入账或存在冲突的历史项。
- 业务身份使用稳定 `posting_key = SHA256(company_id + event_type + anchor_business_key)`，不得包含全局规则版本、科目、日期或生成时间；可变证据、规则、科目/辅助档案和完整分录必须进入 `proposal_revision_hash`。规则变化只能产生同一业务事件的新 revision，不能产生第二个可执行事件。
- 审批和导出必须复用 `VoucherExecutabilityValidator`，客户端状态、`review_tier`、历史 `approved` 或页面按钮均不能绕过服务端复核。至少校验账套/期间、来源文件 hash、proposal revision、Decimal 到分、借贷平衡、科目存在/启用/末级、必要辅助核算、税务证据、重复业务键和未完成批次；阻断项必须以结构化 `blockers[]` 返回并在前端持续展示。
- 导出必须携带 store revision、精确 proposal revision 和显式 item 清单，只允许单一账套、单一期间；先生成不可变 `凭证/批次/<batch_id>/manifest.json + 凭证导入.xlsx`，绑定 facts/科目/辅助档案指纹、行号、计划凭证号、signature 和文件 SHA256，再以一次状态写入关联整批凭证。XLSX 或任一绑定事实变化后原授权立即失效。
- 凭证执行状态必须覆盖 `exported -> importing -> imported | import_failed_confirmed | import_unknown`；批次观察只允许通过幂等 finalize API 整批回写。同一 `batch_id + observation_hash` 重放返回原 receipt；`import_unknown/partial` 只允许后续 `reconcile-only` 只读查账推进，禁止再次导入或把已确认终态降级。确认成功必须覆盖 manifest 全部项目、每项 `observed_state=imported`、凭证号/signature 匹配并携带 `readback_hash`；同时声称 `commit_not_attempted=true` 或 `ledger_absence_confirmed=true` 必须按证据矛盾拒绝。确认 `import_failed_confirmed` 必须证明未点击提交，或携带完整逐项未落账观察、`readback_hash` 和 `ledger_absence_confirmed=true`，不能把“没有看到结果”当成“确认失败”。
- 旧 `PATCH /api/v1/bookkeeping/import-result` 固定返回 HTTP 410 `BATCH_FINALIZE_REQUIRED`。runner 只接受显式 `--batch-manifest`，不得猜测最新 XLSX，也不得直接写状态 JSON；W8 只开放 batch-bound dry-run，真实 Safari `apply`、读回和 `reconcile-only` driver 属于 W10，且每次真实 apply 仍需用户在当回合明确授权。
- 捷锐 facts 使用 `template/grouping/voucher_type/numbering/decimal/aux` 六项独立 readiness；只有 `ready` 能放行所需能力，`not_tested/unsupported/failed` 都必须阻断。未实测的「记」类别、自动编号、小数、分组和辅助核算不得写成既定事实。
- W8 是安全协议与状态底座，不等于 W9 的正式账套 profile、科目/辅助核算和映射人审闭环，也不等于 W10 的真实测试账套导入。代码验收不得自动获得真实状态迁移、审批、导出或账套操作授权。
- W9 的账套 profile、科目表、辅助核算档案和科目映射必须绑定同一 `company_id + ledger_environment + ledger_identity_sha256`；profile 还必须绑定当前科目/辅助目录文件 SHA。测试账套与正式账套、旧采集批次与新采集批次不得混用；绑定不一致时必须停止审批、导出和迁移。
- 映射保存前必须基于当前 CSV 投影和当前/候选 resolver 结果生成零写影响预览；保存时必须重验来源投影、rules/profile/catalog/store 的资源级 CAS，且不得静默覆盖 `manual` 或 `ai_confirmed` 规则。规则变化只能重算 resolver 胜者、胜者指纹、歧义或未命中结果发生语义变化的凭证；无关全局映射版本不得进入 proposal hash。
- 显式 recompute 和映射保存如果得到相同 proposal，不得改写凭证文件或重置 `blocked/rejected`；如果 proposal 变化，只能在同一 `posting_key` 下生成新 revision 并使旧审批失效。
- 映射 v1→v2 与凭证状态 v1→v2 迁移都必须提供确定性 preview hash，apply 必须在同一写锁内重验源 SHA、preview hash、source revision、profile/目录/映射绑定、待重确认数和命令身份；必须保留并校验精确备份 SHA，迁移 revision 只能单调增加。
- 捷锐外部页面自动化不在公开源树保留真实选择器、页面地址、坐标、账套或实测记录。W10 driver 只能在用户当回合明确授权后，于受控测试环境重新采集私有事实；公开源码不得据此自动写入外部系统。

## 银行流水底稿规则

- `src/invoice_hub/bank/` 只读源对账单、回单与 `凭证/` 下的科目表、辅助核算档案和映射规则，输出写在公司资料夹 `银行流水整理/` 与 `做账草稿/`；不得写入 `凭证/` 状态或 W8 批次，也不得连接账套或电子税务局。底稿中的建议分录和草稿凭证都是参考，必须人工审核。
- 适配器按内容识别版式（不按文件名），未知版式或必需字段缺失必须报错或列为未识别，不得用默认值顶替；新增银行只新增适配器，不改变 `models.py` 标准记录语义。
- 方向一律按企业视角：银行对账单“借方发生额”是账户流出，对应企业“贷 银行存款”。金额全程 Decimal 到分。
- 余额勾稽是硬校验：逐行余额、页脚合计、月度断档/重叠、上期期末与本期期初、账面期初差额与重复行都必须以错误/警告进入“校验结果”，不得静默修正。
- 回单匹配先用流水号+金额，再退到日期+金额+方向且候选唯一；多候选标记为待人工指定，不猜。
- 往来角色中人工改过的条目（`source=manual`）优先；自动写入的条目只在发票与关键词都推断不出时兜底，自动推断只补新增户名，不覆盖已有条目；分类依据文本不得写入户名，户名只能放在辅助核算字段。
- 脱敏底稿必须由同一构建函数经脱敏视图产出：自由文本只保留用途关键词白名单；户名用私有密钥 HMAC 化名，公共机构只保留机构类型；账号只留尾号；回单编号、验证码、客户号、业务编号、税号等替换为不可逆标记；源文件名换成序号。金额和日期保留，脱敏底稿用于 AI 辅助或外部协作，不是公开发布物。
- 写出前对脱敏输出做全量泄漏扫描（数字/字母按完整词边界，中文按子串），命中即整体拒绝写出（fail closed）。脱敏密钥与化名对照表只存在私有输出目录，不得进入脱敏目录、仓库或测试夹具。
- 测试只用测试内生成的合成 PDF；真实对账单、回单、底稿和 `往来单位.json` 不得进入仓库。
- 凭证草稿（`voucher_cli draft`）由银行流水、发票明细投影和会计人员提供的 `申报数据.json` 生成；科目按名称路径在当前科目表中定位，找不到或不唯一时编码留空并列入“待补科目”，不得猜相近科目。往来明细按户名唯一包含匹配，品类按账套已有的品类明细（与映射规则一致）匹配。
- 进项税额抵扣按证据推断并在依据中写明：登记在 `已抵扣进项发票` 的按登记月份；所属月未申报的按本月勾选；所属月已申报且应纳税额等于销项税额（未抵扣）的记待认证进项税额，并在第一个未申报月份转入进项税额；其余推定已在当月抵扣，避免重复抵扣。未申报月份的应纳增值税和附加税费在没有申报数时按发票测算并标注“测算”，附加比例取最近已申报月份的实际比例。
- `申报数据.json` 可登记 `勾选清单已登记月份`：这些月份的勾选清单已逐张登记到 `已抵扣进项发票`，未登记的发票即视为尚未勾选，挂待认证进项税额且不自动转出，不得再按“已申报且有抵扣即推定已抵扣”处理。由申报数倒推的抵扣（如缺勾选清单的月份）必须在 `抵扣依据` 中写明“推断”。
- 有账套读回时，发票按税额在读回的进项/待认证（借）与销项（贷）分录中逐一消耗匹配；匹配不到的视为漏记。读回月份早于草稿首月（已结账）时，漏记发票补记在首月 1 日并在待处理中说明；在该月入账前已抵扣的直接记进项税额，但不计入入账月的进项。
- 销售成本按月末一次加权平均结转：期初取读回账套中草稿首月之前的库存商品分录（数量 + 金额），购入取本草稿采购凭证，销售取销项发票数量（按品类定位库存明细）。卖光结转全部余额；卖超照算并在凭证待处理与“库存核对”中写明缺口，不得替人补数。
- 以前月份出库数量与发票不符时（期初应有数量 = 首月之前全部进项发票数量 − 销项发票数量，账面 = 账套期初 + 补记到首月的旧进项发票），在首月生成“更正前期出库数量”凭证：按首月加权单价计价，库存行带数量，差额一行进主营业务成本（小企业会计准则差错更正采用未来适用法）。不得为凑平数量改动已结账月份。
- 读回匹配发票时允许 0.05 元容差：明细逐行税额相加可能与票面差 1 分，严格相等会把已入账发票误判为漏记。
- `--month-end` 把凭证统一记在当月最后一天，只有收付款（单笔银行流水）凭证在摘要前写“yymmdd”实际日期，进销、抵扣、结转与计提凭证不带日期；月内按进货、卖货、抵扣、成本、资金收付（按实际日期）、税费计提排列，分录先借后贷。
- 社保按 `申报数据.json` 的 `社保明细.{月份}.{单位部分, 个人部分}` 在月末计提：借管理费用—管理人员职工薪酬（单位）、借应付职工薪酬—应付职工工资（个人，工资未发时先挂借方待扣回），贷应付社会保险费；无明细不计提、不按费率猜拆分。
- 工资社保页面（WS-05 第三阶段，`services/company_payroll.py`）：只读公司资料夹工资社保子目录里电子税务局的“社保费应缴明细”，Excel 按两行表头的名称识别列（单位部分 / 个人部分分组），PDF 只读文字层并要求每行恰好 11 个数值；图片本版本不识别（需 OCR，见 OCR-01），只列出并提示手工录入，不得猜测；版式对不上的文件列为未识别。“单位 + 个人 = 合计”“基数 × 费率 = 应缴”（单人时）在后端计算，误差 1 分以内，不成立时页面标红但不改数。只有用户确认某月后才写 `申报数据.json` 的 `社保明细.{月份}`（单位部分、个人部分为所确认险种行的应缴合计，另存来源与险种明细），整文件带 SHA-256 revision 原子重写并保留其他键，文件损坏或不存在时拒绝；草稿计提沿用上一条规则。人员姓名、证件号默认脱敏返回，只有页面显式请求时返回原值，不写日志。
- 草稿不自动生成工资计提、未提供申报数的企业所得税和期末损益结转，并在审核表说明中列出。
- 已在捷锐入账的月份用 `--booked` 传入人工从“序时账”页复制的制表符文本（私有，放 `做账草稿/`）。这些月份不再生成发票、待认证转出和月末计提凭证，只把对不上的银行流水生成补记凭证，凭证号接在账套该月最大号之后，导出也沿用该起点。银行分录先按同月同方向同金额一对一对回流水，再只在摘要点名的对方流水中找合计相等的组合（账套曾把多笔来款合成一张）；对不上的账面银行分录列为“账有银无”，不得按相近金额硬配。
- 账套新建科目后，草稿与导出可用 `--ledger` 指向私有读回快照；快照只放公司资料夹 `做账草稿/账套读回/`，不得回写 `凭证/科目表.json`（它仍由 InvoiceHub 采集流程维护）。
- 对账单行号按整份对账单的位置编号：中国银行每页序号重排，按序号编号会撞号并让分类、对方户名互相覆盖。
- 审核表必须给出“银行对账”（每笔流水 → 已入账凭证/本次凭证/补记/账有银无/未生成）和“月度核对”（对账单收支合计 vs 账套已入账 + 本次凭证的银行存款借贷合计，差额为 0 才算一致；无对账单的月份标“缺对账单”）。已申报月份同时列出申报应纳增值税与“发票销项 − 本表进项”的差异，不为 0 表示申报用到的发票未收集全，不得把差额塞进分录。
- 默认摘要为“动作 + 对方简称 + 用途”的短句（如“付某某材料款”“缴6月税费(含Q2)”）；与往来单位/个人的资金收付一律写“收X往来款”“还X往来款”，不按借款、垫入款区分（用户在账套中的统一写法），可在审核表逐行修改并按行导出；对账单、回单、发票原件以超链接列出页码，链接只指向私有公司资料夹。
- 导出（`voucher_cli export`）只处理“审核=通过”的凭证，逐张校验日期属月、借贷唯一且平衡、金额为正、科目存在启用且为末级、必填供应商辅助核算；任一凭证不合格则该月整月不写出。导出列与 `凭证/导入/模板原件.xlsx` 一致，凭证号按月重新连续编号。同一凭证签名已导出过时默认跳过，防止重复导入。
- 捷锐导入实测（2026-10-21）：“制单人”为必填，缺失时整张凭证以“业务错误：制单人为必填”拒绝，因此 export 必须显式传 `--preparer`；同一次实测中科目编码、借贷金额、数量/计量单位与供应商辅助核算未报错。
- 账套某月已有凭证时，导出须用 `--after YYYY-MM:NNN` 显式给出已用到的号，从下一号连续编号；不按“哪些没通过”推断起点。同日同分录的多张凭证按出现次序区分签名，不得被当作重复导出跳过。
- 导出编号在剔除不通过的凭证后连续重排，因此捷锐凭证号可能与草稿凭证号不同；补导或核对某张凭证必须按日期、摘要和分录内容定位，不得按草稿号定位。导入失败的凭证在捷锐留下空号，补导用 `--after` 接上一个号。
- 往来科目按账套实际启用的辅助维度带户名（如某些账套应收账款启用的是“供应商”而非“客户”维度）；科目表快照的辅助维度须与账套读屏一致，导入实测发现不一致时先修快照。
- 导出文件交给会计人员在账套中手工导入；既有捷锐实测只覆盖本页注明范围，不代替当前 WS 页面导出与目标账套导入验收，首次在目标账套只导入一张核对。人工最终使用的科目按槽位写入私有 `做账习惯.json`，下次生成优先沿用；习惯、导出记录和草稿都不得进入仓库或测试夹具。
- 页面审核凭证草稿（WS-05 第一阶段，`services/company_vouchers.py`）：只读写公司资料夹 `做账草稿/` 内非链接的 `凭证草稿_*.xlsx` 的“凭证审核”表，允许编辑摘要、科目编码（同步科目名称，未知编码清空名称）、借贷金额、供应商与审核列，并在已有凭证内增删分录；结构变更须遵守下方 P3 保护，不动其它工作表；保存必须携带读取时的文件 SHA-256，不一致整批拒绝且不自动重放。审核通过的校验必须用导出同一个 `jierui.validate`，以该草稿生成时用的科目表（`草稿生成参数.json` 的 `ledger`：`做账草稿/账套读回/` 下列出的 `科目表_*.json` 快照或 `凭证/科目表.json`；命令行生成、没有记录的表用最新快照，与改记入期重新生成同一默认）与 `辅助核算档案.json` 只读校验，读回结果带 `books_source`；缺科目表或记录的快照已不在时一律不能审核通过，不得换用另一份科目表；任一要通过的凭证校验不过时整批不写；改过的已通过凭证若本次未重新审核，必须清空“通过”。页面不写 `凭证/`、不连接账套。页面列表统计、审核、保存与导出用同一份科目表（2026-11-17 统一）；命令行导出仍按 `--ledger` 参数。
- 页面凭证草稿第二阶段（所属期 / 记账日期）：凭证移到另一个月时必须接在该月已有凭证号（及同一次保存中先移入的凭证号）之后重新编号，不得沿用原号——导出按“月份 + 凭证号”分组，撞号会把两张凭证合成一张；不能选未来月份；记账日期不在所属期内可以保存，但 `validate` 会阻止审核通过；移动或改日期视同改动，原“通过”须重新审核。草稿的“月度核对 / 银行对账 / 库存核对 / 待补科目”只读展示，页面不改这些表。
- 页面导出（WS-05 第二阶段）：必须直接调用 `jierui.export`，输入与 `voucher_cli export` 解析的一致（该草稿生成时的科目表，同上一条；`辅助核算档案.json`、`凭证/导入/模板原件.xlsx`，输出到 `做账草稿/`），不得另写一套导出或放宽整月拦截、重复导出跳过；只在用户显式确认、填写制单人后执行，且文件 revision 必须仍是用户审核时的版本（在导出锁内复核）；`after` 只接受用户填写的“账套该月已用到的号”，不得按通过与否推断；不提供“允许再次导出”；返回只含文件名，不返回本机路径；同一进程内导出串行。导出文件只交给会计人员在账套中手工导入，页面不连接账套。
- 通用凭证导出（BK-01，`bank/export_profiles.py`）：导出前的业务规则（只导“通过”、整月拦截、按月重新编号、`after` 接号、重复导出跳过、制单人必填、习惯学习）只在 `jierui.export` 一处，各格式只替换最后写文件一步；已导出过的凭证换一种格式也跳过，防止同一凭证导入两个账套。捷锐配置（已实测）必须与改造前的导出逐单元格一致并沿用 `凭证/导入/模板原件.xlsx` 的列序；柠檬云（表头取自第三方模板）与用友 T3/U8 文本（`填制凭证,V800`，GBK，按位置 21 个字段）为实验配置，页面必须写明“未经实际导入验证”并建议先导一张；其他软件由用户把自家账套下载的空白模板放进 `做账草稿/导出模板/`，按表头同义词对列，对不上的列留空并列出，缺必需列（日期、凭证号、摘要、科目编码、借、贷）的模板不可用。辅助核算只有名称时，按编码引入的格式留空编码，不拿名称顶替。GB/T 24589 是审计导出标准，不作为导入目标。
- 页面生成草稿（WS-05 第二阶段）：必须直接调用 `bank.vouchers.prepare` 与 `jierui.write_review_xlsx`（含命令行的说明页），与 `voucher_cli draft` 逐单元格一致；起止年月不能是未来月份；序时账读回与科目表快照只能从 `做账草稿/账套读回/` 列出的 `序时账_*.txt`、`科目表_*.json` 中选，不接受任意路径，科目表快照不得回写 `凭证/科目表.json`。覆盖已有同期审核表前必须先完整备份到 `做账草稿/历史/`，现有表无法读取时拒绝覆盖。沿用审核只按凭证来源配对（发票号；银行流水 row_id + 借方合计；其他按“来源 + 月份 + 科目集合”），不得按凭证号配对；只有导出签名（日期 + 科目 / 借 / 贷 / 供应商）不变才沿用“通过 / 不导入”，内容变了的只沿用改过的摘要（行数一致时）并列入需重新审核。与导出共用同一进程内锁。
- 改记入期（WS-05 第二阶段，凭证属期是生成数据，只更正数据）：发票的记入期人工调整存公司资料夹 `做账草稿/记入期调整.json`（发票号 → 月份、原因），带 revision 写入，损坏时拒绝覆盖且生成失败、不得当作没有调整；`build_drafts` 在 `book_month` 处优先采用调整（不再按读回判断是否已入账，调到草稿范围外的不进本表），页面与命令行生成都读这份文件；抵扣月份仍按开票月与申报数据判断，记入早于可抵扣月份的进项挂待认证；范围前开票、记入本草稿某月的票不得再计入首月期初应有数量。调整后按该表上次的生成参数（`做账草稿/草稿生成参数.json`；命令行生成的表按文件名起止月与默认值）重新生成并沿用审核。不移动发票文件；银行流水按对账单入账日记账，不提供单笔改记入期。
- 属期文件夹核对与移动文件（WS-05 第二阶段，文件放错属期时真的移动）：只用于进项抵扣（`.xlsx`）与银行流水（`.pdf`）子目录。文件期间只按内容取得（抵扣清单的税款所属期、单月对账单的起止日期），属期文件夹名（“2026-07”“6月”“10月份属期抵扣项”）只用于提示“可能放错”，不得参与任何计算；没有单一属期的文件（空导出、跨月对账单）不按文件夹推断。移动必须先列计划、用户确认后执行：按文件签名（设备、inode、大小、时间）复核，逐文件先 fsync 记录意图再改名、后记录结果，确认响应丢失只读执行日志，不得重复确认或自动重试；目标只能是同一子目录下已有的属期文件夹或新建的 `YYYY-MM` 文件夹，不覆盖同名文件，拒绝链接与越出子目录，与当前监控目录重叠时拒绝；计划与日志存 `runtime/local_state/source-moves/`，返回页面的只有子目录内相对路径。

## 公司清单（WS-07）

- 公司资料夹选择（WS-02）使用独立 `pick_company_directory`，请求只接受空对象 / 空 body；选择只返回草稿，不登记、不创建目录、不改变 watch_dir。host 精确 origin / ownership、取消保留草稿、private 错误与超时脱敏 503；页面关闭或草稿改变后丢弃迟到返回。
- 从零新建是独立确认流程（`CompanyRegistryService.setup` / `company_setup.py`）：已有父目录 + 不存在的单层公司文件夹名 + 六类相对映射，计划只写 runtime；确认重验 registry revision、父目录身份、plan_hash 与 5 分钟有效期，先持久化排他执行标记 / 每步意图再 mkdir，观察后保存结果。只创建空目录，不覆盖、不链接逃逸、不与已登记公司或活动 watch_dir 重叠，不切换监控；失败不删除已创建目录，登记后事件失败按未知处理。重复确认和重启后的未决标记只查询，不能重放。
- 映射修改只保存六类资料的相对路径，不移动或重命名任何已有文件；缺少目录另走原补建预览 / 确认。Windows 保留名和尾句点拒绝，六类路径仍不得相同或互相嵌套。

- 公司清单与单目录设置分开存放在 `runtime/local_state/companies.json`；任何清单读写都不得改变活动 `watch_dir`、TargetProfile 或 monitor，监控仍只有一个目录。`monitored` 只是标记活动目录落在哪家公司内，不能据此显示 daemon“实时监控中”；工作区侧栏显示“当前监控目录”。没有清单时产品行为与之前一致。
- 清单只由 `CompanyRegistryService` 在共享 RLock 内写入，写请求必须携带当前 `revision`；文件不是合法 v1 清单时必须保留原文件并拒绝写入，不得当作空清单覆盖。
- 普通登记的公司资料夹根目录必须已存在（从零向导先按确认计划创建，再登记），不同公司的根不得重复或互相嵌套；六类子目录保存为根内相对路径，拒绝越界写法，彼此不得相同或嵌套。登记时的自动识别只取唯一、无歧义的命中，命中多类的文件夹不猜。
- 补建缺失子目录必须先预览，再以预览的 `plan_hash` 和 `confirm=true` 执行；执行时重算计划，任何变化都要求重新预览。只新建空目录，不移动、删除或改写任何文件；链接或越出根目录的路径不创建。删除公司只删清单条目。
- WS-02 计划同时绑定根与每级现有目录的设备 / inode 身份；同名替换也须重预览，根内链接 / junction 与父路径同名文件均阻断。补建逐层核对已确认父身份，POSIX mkdir 使用受校验目录句柄；Windows syscall 级并发仍须实机验收。新建登记前复核全部已创建目录，变化则保留现场、不登记。清单 / 新建日志的嵌套结构损坏不能按默认映射继续执行或被写入覆盖。
- 纳税人身份按生效月份记录；未登记即“未设置”，不得默认一般纳税人。成本开票参考的纳税人类型以清单为准，细则见[成本规则](COST_ANALYSIS.md)。
- 公司发票账簿（WS-07 第 3 步发票部分）：只读两个目录的上次投影并套用手改字段；同票多格式只计一次；金额未识别、格式间冲突或“不含税 + 税额 ≠ 价税合计”的票必须单独列出、不计入，不得猜补；守恒校验在后端计算并随结果返回，不成立时页面必须醒目显示、不得隐藏；结果标注票面口径，不得称为利润或应纳税额；不按公司名称自动剔除发票，只提示购买方/销售方不一致。
- 公司账簿的银行流水（WS-07 第 3 步银行部分）：只在请求时只读解析银行流水目录的对账单，不得写入公司资料夹或 `银行流水整理/`、不得后台扫描；目录列不全时整体不汇总，不得只汇总一部分月份。没有对账单的月份必须标为缺失、余额留空，不得按 0 或上月余额补齐；期初 + 收入 − 支出 = 期末与对账单自检在后端计算，不成立时页面必须标红。银行口径与票面口径分开返回，银行校验不并入发票守恒校验。
- 抵扣核对（WS-07 第 4 步）：只读成本发票的上次投影和进项抵扣目录里的“用途确认信息”导出，不写任何文件；只认表头齐全、有税款所属期的“发票”表，其它文件列为未识别，空清单不按文件夹名推断所属期。只有“已勾选”的行算勾选；清单有目录无、目录有清单无（专票）、重复勾选、税额不一致必须单独列出，校验在后端计算、不成立时标红。结果标注“已勾选不等于已申报”，不得把清单当作申报或抵扣的最终依据，也不得据此改写做账草稿。没有勾稽关系的两类资料必须拒绝比较，不得拼凑关联。
- 进销存（WS-07 第 4 步）：只读两个目录上次的成本投影（`read_only_inputs`，不得调用会刷新或重写工作簿的 `snapshot`）；库存按品类计算（2026-11-11 用户决定）：品类 = `bank.vouchers.goods_family`（标准名称）+ 单位，与账套库存商品明细、做账草稿同一口径；品目表标准名称 + 规格 + 单位只作下拉细分，只列购入、销售数量与购入金额，期初与成本不得分摊到规格，各规格之和必须等于品类合计；销售成本必须调用 `bank.vouchers.cost_of_sales`，不得另写一份加权平均；科目表取最新的 `做账草稿/账套读回/科目表_*.json` 快照，没有快照才用 `凭证/科目表.json`，没有序时账也读取（`account_code`、电梯判断）；做账不记库存商品的行（`bank.vouchers.purchase_family_treatment`：燃油记费用，库存商品下没有电梯明细时电梯记固定资产）进销项两侧都不得进入品类，必须列入 `excluded` 写明原因并以 `non_stock` 提示披露进项金额（2026-11-17，BUG-05），不得只提示不排除；期初只在公司资料夹 `做账草稿/账套读回/序时账_*.txt` 有期初月份之前的月份、且该科目表能唯一定位“库存商品”时，用 `stock_opening` 累计取得，此时期初月份之前的发票不再计入；否则按 0 起算，两种情况都在结果中标注；读回文件只在请求时只读，损坏或缺科目表只降级为 0 起算并说明原因；账套分录没有单位而该品类有多个单位时不得猜，列为未计入期初；同一品类有多个单位时分行并提示；卖超、销项品类在进项与期初中都找不到必须照实列出，不得凑平数量；进货额口径与成本页开票参考一致（不含税 + 不可抵扣税金）。
- 往来核对（WS-07 第 4 步）：只读发票投影与对账单；户名只在唯一命中（相等或 ≥4 字截断前缀）时归属，命中多家不归属；匹配只用“红冲同额原票 → 一对一同额 → 唯一 2—3 张组合”，多组可行时不对应；剩余流水列为未逐笔对应，不得按比例或时间猜分摊；提供显式期初时从快照月起累计且排除更早来源，未提供时沿用零基线参考并标注未提供；损坏或超出覆盖期明确披露，不冒充真实期初。余额与笔数守恒在后端从原始清单复算，不成立时标红。
- 项目汇总（WS-03）：项目取自发票备注（PDF 文本或 XML `<Remark>` 提取的“备注项目名称”），经单跳无环 `aliases` 映射后一张票仍有多个名称时不择一、列入未归属；支持对任意发票（含备注识别发票）人工改派项目、显式移出未归属（`unassigned: true`）或恢复备注，以及先预览 `preview_hash` 再确认的项目重命名/合并（可同步 `服务成本归集.json`）；人工归属与别名写入公司资料夹根目录 `项目归属.json`，只在用户保存时写、带 revision 与锁，汇总与监控不得读写或覆盖它，绝不修改源发票，损坏或含环文件拒绝覆盖；未归属单列，不得分摊；合计必须与发票账簿一致。
- 发票标签（WS-06）：定义存本机 `runtime/local_state/invoice_tags.json`，标记存公司资料夹根目录 `发票标签.json`，只在用户操作时写、带 revision；标签只用于显示和筛选，不得写进源发票、CSV 或投影字段，不得影响金额、状态与勾选合计；删除标签必须同时移除已打的标记。
- 同号检查（WS-04）：只用于没有勾稽关系的两个发票目录，可跨两家公司；只读两边上次投影，只按发票号码比对，不按金额、日期或户名关联，不得把同号写成重复的结论——两家公司一方开具、一方取得的是同一笔交易，其余同号标为疑似重复、由人工核对；同一公司有勾稽关系的组合必须拒绝并改用勾稽核对；没有号码的发票单列，不参与；两家纳税人身份不同时提示税额不可直接比较。
- 按公司只读目录（WS-07 第 2 步）：GET 查询非活动目录只读上次投影并在请求时提示是否过期，不得在 GET 中后台扫描、重建或写入其投影，也不得为它创建 TargetProfile 目录；过期判断必须有界、不修复状态文件（不得用会建目录和修复文件的 `MonitorState`）。只读行不得接入预览、打印、改名、删除等动作；要实时监听、弹窗通知或执行源文件动作，用户须先把它设为监控目录。
- 非监控公司目录按需只读刷新（2026-11-23）：登记已有公司资料夹成功后或用户显式点击“读取数据 / 更新数据”时，可通过独立的 `POST /api/v1/companies/{company_id}/refresh-data` 后台增量读取该公司三类发票目录；必须与目标 profile 共用 `sync_write_lock`、跳过当前活动 `watch_dir`、以 `export_to_source=False` 仅把完整代际写入本机 `runtime/targets/<id>/workspace/`，绝不切换监控目录、不启动第二个 daemon、也不向未监控源文件夹写入任何导出文件。
- 公司自定义与默认文件夹全生命周期及基准功能指向（2026-11-25，`services/company_folders.py`）：保持 `companies.json` `schema_version: 1` 向后兼容，支持对公司内自定义目录与默认 6 类目录执行新建空文件夹（预览 `plan_hash` + 显式确认）、跨路径导入（公司内 `inside_root` 或公司外 `external`，拒绝链接/系统根/公司间重叠）、修改显示名与硬盘原子改名（监控或写锁冲突拒绝、清单失败自动回滚）、非破坏性移除/隐藏与默认恢复、以及原生回收站移入（有界扫描统计 + `plan_hash` + 显式勾选确认 → `move_to_trash`，严禁永久删除降级）。自定义目录可指定 6 类默认功能基准或 `general`，开放对应单目录功能（后台刷新、发票列表、监控预览/打印/回收站、同号检查、属期核对与移动、银行版式、只读工资社保预览），但默认与公司级总账、成本 V2、凭证草稿隔离防重复计账；公司内自定义目录可通过二次确认一键晋升为主标准槽位（原主槽位保留为自定义目录，不移动/删文件）。

## WS-04 回单只读预览

比较页面请求时只读银行目录回单，复用 `discover/match_receipts`，不写银行底稿或账套。回单 → 流水 → 发票只沿后端匹配 ID，不按金额 / 户名另猜。PNG 预览能力绑定公司、目录身份、唯一源文件 SHA 与版本，来源改变必须失效；重名不可随意择一，链接 / junction 拒绝。银行 / 抵扣的文件签名缓存同时包含 ctime、dev / inode，解析中变化不发布。

## 工作区期间与预览（B4，2026-11-17）

期间索引只读审核表并复用导出校验/签名规则，损坏表单列诊断；顶层统计不授权合并多个审核表导出。页头所选月份必须同时约束导出预览与正式导出；空月份明确表示当前审核表全部期间。dry_run 复用正式导出的整月阻断、重复跳过、编号与列映射，最多五行，不能写文件、已导出历史或学习习惯。正式导出仍二次确认；工作区 request_id 的意图必须先持久化，再产生任何正式文件；未知结果只查询回执，不因未找到记录就重放。兼容旧无 token CLI/API，不改变真实账套授权边界。

## P2 公司版式与税费记录（2026-11-17）

银行映射只接受服务端签发的公司内文件身份，源/目录/映射/revision 变化使预览失效；余额链多解或断开、账号不唯一不得保存。P3 后确认档案由公司账簿/往来、显式公司 CLI 与凭证生成共用，新文件重新校验；未明确公司根时不得猜父目录。对账状态遇解析错误/源过期返回未知，缺完整发票月不得标未匹配。税费记录独立于草稿，不因银行扣款或测算自动标已申报/已缴；真实账套和报税仍需独立授权。

## P3 银行档案与分录结构（2026-11-17）

- 固定账号是私有业务数据，银行版式档案不可直接分享；保留前导零，出现可识别账号列时即使未映射也须核对一致。不能从文件名猜账号。CLI 显式 --company，公司页面生成使用登记的银行目录映射；含版式档案的凭证生成拒绝公司根外银行目录，避免把本方账号套入另一公司。目录列不全拒绝，不以部分文件出具完整账簿。
- 已有凭证内可增删分录，但不能删除整张凭证；最终1—500行、一次最多新增100行。新增行不得携带来源、数量或学习槽位；删除首行后来源与超链接转到存留首行。带读取SHA、与导出/生成共锁，改过的已通过凭证须重新审核，审核仍用同一导出校验，拒绝整批不写。含公式/合并审核表拒绝结构编辑，不能猜跨表引用平移。

## WS 后端收尾保护（2026-11-19）

社保确认与草稿生成 / 编辑 / 导出共用进程内写锁，读取 SHA、校验、替换不能在本进程内交错；替换前重验 SHA 与公司 / 草稿目录身份。申报文件有界且无链接读取，`社保明细` 的嵌套结构损坏不能当空对象覆盖。非法数值 / 月份 / 人数 / 费率整批拒绝，每个险种至少一方应缴已知，不能把脏值清空后按零计提；一方不适用的空值和显式零保留。该锁不承诺外部 CLI / 编辑器跨进程事务，Windows / 网络盘真实语义仍须独立验收。守护见 `test_company_payroll.py` 的损坏、并发、目录替换、外部改动与混合批次测试。
