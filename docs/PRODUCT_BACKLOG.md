## 怎么维护

一般软件团队用“待办清单 → 版本计划 → 开发 → 验收 → 关闭”管理未来工作，本仓库按同样流程：

1. **登记**：发现问题或需求时新增一条，先写清“问题与证据”和“验收标准”，方案可以粗略。没有证据或验收标准的条目不排期。
2. **分级**：按影响与成本给优先级——`P0` 影响数据正确性或合规、必须下个版本做；`P1` 明显提升效率或降低风险、下个版本优先；`P2` 有价值、视容量安排；`P3` 想法，暂不排期。
3. **排期**：规划版本时从 `P0/P1` 中挑选，把“目标版本”写成具体版本号，状态改为“已排期”，并在开工时按 [AGENTS.md](../AGENTS.md) 建功能分支、读对应功能规则。
4. **关闭**：实现并通过验收后状态改为“已完成”，注明版本与 CHANGELOG 小节；放弃的条目改为“不做”并写原因，不直接删除，便于追溯。

状态取值：`待评估` / `已排期` / `进行中` / `已完成` / `不做`。

## 条目格式

| 字段 | 内容 |
|---|---|
| 编号 | `领域-序号`，如 `COST-01`；缺陷用 `BUG-序号`；编号不复用 |
| 标题 | 一句话说明要改什么 |
| 优先级 / 状态 / 目标版本 | 见上；未排期时目标版本写“待定” |
| 问题与证据 | 现状是什么、在哪里看到、影响谁 |
| 方案 | 建议的做法；可以列备选 |
| 验收标准 | 可检查的结果，最好能写成自动化测试 |
| 影响范围 | 涉及的模块、接口、页面与必须同步的规则/文档 |

### COST-01 开票参考成本基数改为“未开部分的剩余库存”

- 优先级 / 状态 / 目标版本：P1 / 进行中 / 待定。V2 工作区、显式迁移和独立对照表导出已接入，待真实金额与平台验收。
- 问题与证据：参考除税单价 = 该分组**全部历史进项**的加权均价 × (1 + 加价率)。已开票卖出的批次仍留在均价里，进价变动时参考价滞后。2026-10 用一家商贸客户 Q2—Q3 的 32 行销项回测：后期参考价仍混入数月前的进价。
- 方案：2026-11-05 确认默认用“结存加权单价”（月末一次加权逐月滚动后的结存单价，与做账结转同一函数），并列显示“最近一次进价”；先进先出因销项无批次信息且与做账口径不一致，首版不做。保留现有全量均价作为对照列，避免旧用户口径突变。详见[成本分析 v2 设计 §4.2](COST_ANALYSIS_V2_DESIGN.md#42-成本口径)。
- 验收标准：低价和高价批次跨月且已部分销售时，V2 成本基数等于按月结转后的结存加权单价。V2 对照页、迁移 API 与同一修订导出的 XLSX 逐行一致。经典页面、v1 API 和兼容工作簿按原口径核对，迁移后旧已开快照仍可复核。
- 影响范围：`projections/cost_analysis.py`、开票参考 sheet、`/costs` 页面、API 契约测试、COST_ANALYSIS 规则与数据算法 §9。
- 当前证据与剩余验收：`test_company_costs` 覆盖跨月结转、历史身份以及来源过期、卖超或零结存时的空值。工作区已显示品类库存口径、旧新价格差额和迁移选择，真实资料逐行对照与双平台附件下载待验。

### COST-02 品名别名归一，同规格不同叫法合并分组

- 优先级 / 状态 / 目标版本：P1 / 进行中 / 待定。品目表首版于 11 月 8 日通过真实目录副本验收。当前开发线已接入显式库存科目对照、服务类型与别名候选，新增范围待真实与平台验收。服务品目与凭证科目归集另见 [COST-07](#cost-07)。
- 问题与证据：分组键含 `内部项目名称`。不同供应商对同一材料的叫法不同（如“三级抗震盘螺HRB400E”与“盘螺”），同规格被拆成两组，各算各的参考价；销项开“盘螺”时找不到对应进项组。
- 方案：2026-11-08 用户确认不在本系统另建科目体系（账套是真值）。首版品目表按名称维护标准名称（改名即合并）、类型（货物 / 费用 / 固定资产）与可选销项税率，存于 watch_dir 状态文件；分组前把名称换成标准名称；规格只统一全角半角与空白（不改大小写），不去掉 E 后缀（`18E` 与 `18` 是不同牌号），不自动猜测同品。第二层科目对照从读回的账套科目表选择（可选），做账时接入并取代 `bank/vouchers.py` 写死关键字的 `goods_family()`。详见[成本分析 v2 设计 §3.1、§3.3](COST_ANALYSIS_V2_DESIGN.md#33-品目表首版范围cost-022026-11-08-开工)。
- 验收标准：首版——改名合并后两组数量与金额相加正确，合并前已保存的已开数量与快照金额合计不丢；改回原名可拆回；非货物不进开票参考；品目税率只影响该品目；未配置品目表时分组键、金额与现在逐行一致。第二层——同一库存科目下各品目结存合计等于做账库存核对的科目结存，未对照的品目显示“未对照”。
- 影响范围：分组键与状态迁移（数据算法 §9.2）、`bank/vouchers.py` 的 `goods_family()`、开票参考 sheet、`/costs` 页面、状态 JSON 兼容测试。

### COST-03 由销项发票自动累计已开数量并显示实际加价率

- 优先级 / 状态 / 目标版本：P1 / 进行中 / 待定。经典成本表保留手填快照，按品目表归一后比较销项；V2 已分列实际销项与手填快照，待真实业务目录与 Windows 验收。
- 问题与证据：已开数量靠手工填写，容易漏填；开票后看不到“实际售价相对成本加了多少”。回测发现多数销项恰好等于参考价（加价 8.00%），少数低于参考价，但页面无从发现。
- 方案：读取当前目标的销项发票（outbound 目录）明细，按 COST-02 归一后的分组自动累计已开数量；每行显示实际售价、实际加价率，与参考加价率的差异着色；手工数量作为覆盖值保留并标注来源。
- 验收标准：销项比对数量等于归一后的实际销项合计，经典页“按销项更新”先改草稿，经确认保存才更新快照。V2 有实际销项时取实际值，否则显示手填快照。实际加价率与按对应成本口径复算的结果一致。
- 影响范围：销项发票读取与目标路径（`outbound_invoice_dir`）、开票参考状态、`/costs` 页面、API 契约测试。

<a id="cost-04"></a>

### COST-04 开票参考未开数量与账面库存核对

- 优先级 / 状态 / 目标版本：P2 / 对照、期初、月末差额与前端已接入，真实/双平台验收待做 / 待定
- 问题与证据：开票参考的“未开数量”只来自发票，凭证草稿的“库存核对”只来自账套读回，两边不互通；账套出库记错（如按购入数量而非销售数量出库）时，参考表看不出来。
- 方案：明确库存科目对照和期初，按品类+单位对照发票滚动与账面期末数量/金额，差异及覆盖原因可见；规格只展示明细、不分摊期初/成本，无可信账套数据明确待核对。
- 验收标准：合成场景中账面少出库 N 吨时，对应行显示差异 N；无账套数据时页面与现在一致。
- 影响范围：成本分析与 `bank/vouchers.py` 库存核对的只读衔接（不得写 `凭证/`）、BOOKKEEPING 与 COST_ANALYSIS 规则。
- 2026-11-19 衔接基础：V2 已复用进销存品类 + 单位结存及其守恒检查和账套期初读取，规格不分摊期初；这不等于完成与账面期末差异核对。仍需确认库存科目映射、连续账套覆盖与前端差异说明；验收须用合成账面少出库 N 的场景得到明确差额，未映射/无数据不得冒零。影响 `company_costs/company_inventory`、公司比较与后续 V2 前端。
- 2026-11-21 当前进度与剩余：显式品名→末级库存科目、确认期初、完整月份声明已共用于 V2/进销存/草稿；V2 月末差额通过合成少出库 1 吨/100 元与零差额用例，缺月/无基线/重复行/单位冲突均待核对。前端须展示对照、覆盖、账面减发票的数量/金额差额及不可核对原因，不按规格分摊或把旧手填未开量当账面；真实与双平台验收仍未完成。

<a id="cost-05"></a>

### COST-05 增加合同价/市场价参照与固定加价率提示

- 优先级 / 状态 / 目标版本：P2 / 进行中 / 待定（固定/合同价、人工市场参照、版本绑定依据归档与一致加价率样本已接入，待真实/平台验收）
- 问题与证据：参考价只由成本加价得出，售价完全跟随成本。若一段时间内所有销项都恰好等于“成本 × 固定倍数”，且进销品名、规格、数量一一对应，在税务风控里容易被关注；用户需要能对照合同或市场价并保留依据。
- 方案：每行增加可选的“合同价/市场价”录入与偏差显示；当选定期间内销项实际加价率全部相同（可配置阈值）时给出提示，提醒留存合同定价条款、送货与签收单据。提示只作风险提醒，不改变金额。
- 验收标准：录入合同价后显示偏差百分比；合成数据全部 8.00% 加价时出现提示，有差异时不出现；提示文案不含真实业务信息。
- 11 月 22 日核对旧验收项时，已找到固定价试算和实际加价率一致提示的回归。“合同价偏差百分比”仍缺单独的页面结果与验收证据，需先明确与哪一项价格比较，再核对数值。一致性提示当前使用固定精度，页面可调的是采购波动和最低毛利阈值。
- 影响范围：开票参考状态字段、`/costs` 页面、API 契约测试、COST_ANALYSIS 规则。
- 2026-11-21 后续：实际加价率一致提示已接入，至少三个同票同品目样本，采用原月实际成本、到0.01个百分点比较；未知样本阻止全期间结论，来源与依据可查，不据此判断税务违法或自动改价。自动行情源仍为后续设计（证据：当前市场价只接受人工来源与有效期；验收须定义可靠来源、失败/过期保护和归档证据，影响定价/监控/API/前端）。真实资料和双平台附件下载未验。

### COST-06 成本分析 v2：公司级品目台账 + 灵活定价规则

- 优先级 / 状态 / 目标版本：P1 / 进行中 / 待定（2026-11-21 既定V2开发范围已接入本地开发线，含服务项目毛利与两类价格提示；未推送/合并/发布，真实/双平台/成品验收待做）
- 问题与证据：现有开票参考只有“全量加权均价 × (1 + 单一加价率)”，默认 8% 兜底；不读销项、不与做账库存互通，无法表达按客户 / 项目定价、目标毛利、固定加价、合同价、阶梯价、最低毛利保护等常见定价方式（2026-11-03 用户反馈“加价率相对死板”）。
- 方案：见[成本分析 v2 设计](COST_ANALYSIS_V2_DESIGN.md)，2026-11-05 用户确认的决策记在其 §0。公司级品目台账与做账库存同源（品目挂库存科目，科目层结存一致）；成本默认结存加权单价并列最近进价，进项税是否进成本按纳税人类型与票种；销项税率按公司与品目设置（含小规模 3% / 1%），特殊计税首版只提示；定价改为规则——首批加价率、目标毛利率、固定加价额、目标价 / 合同价 + 取整与最低毛利保护，第二批阶梯与市场价参照——按“单行 > 客户 × 品目 > 客户 > 品目 / 公司默认”取用，同层生效期不得重叠，带试算与可解释代入式；页面以“先选客户再给价”的定价助手为主；已开部分以实际销项为准，手工补填才锁快照。COST-01—05、BUG-01 是它的分步实现。
- 验收标准：每种定价规则、优先级、生效期与冲突、取整和最低毛利保护有单元测试。两类纳税人均逐行显示 v1 历史均价与 V2 结存加权定价的差额，用户明确选择是否沿用旧人工加价率。核对迁移前后旧已开快照、各版本页面与对应导出、成本分析与做账库存及比较页的科目层结存、v1 API 兼容字段。[设计第 8 节](COST_ANALYSIS_V2_DESIGN.md#8-兼容与迁移)
- 影响范围：`projections/cost_analysis.py`、`projections/costs.py`、`bank/vouchers.py`（`goods_family`、`cost_of_sales` 共用）、成本状态迁移、公司设置（纳税人类型）、`/costs` 页面、工作簿、API 契约测试、COST_ANALYSIS 规则与数据算法 §8—9。
- 当前证据：独立 `cost_pricing/company_costs` 与公司 V2 API 的合成测试覆盖六种规则/税额守恒、数量/金额分档、市场有效期/取整后底线、优先级/期间、旧人工行迁移、已开快照不变、独立规则保存、来源/目录/公司隔离与同进程冲突。市场证据仅作用本次报价，变更后拒用旧确认；规则文件不被 monitor/v1 重写，GET/quote/preview 不写公司资料。

## 多公司工作区（WS）

- 方案：系统挂载 SMB 只读适配先行，SFTP 后续；VPN/跳板机等网络路线分期。来源身份绑定连接账户、根与版本；完整副本本地提取/预览，凭据走系统安全存储，主机指纹变化阻断。断连保留最后完整汇总与已完成缓存，不以读失败推断删除。详见[连接与缓存设计](SERVER_CONNECTION_AND_CACHE_DESIGN.md)，在[已有原型](design/workspace-sidebar-prototype.html)侧栏点击“服务器链接（试验版）”。
- 验收标准：配置/收藏/SSH 核对、右栏目录与文件标签/蓝条、展开/收起/主内容区内放大还原、目录名标签/子目录下拉/面包屑、当前目录统计与空内容提示、本机公司栏和模块不变；未来接入验全部模块同来源同代际、重连复用/异来源隔离、已缓存与未缓存离线预览及断连恢复；真实 SMB/SFTP 测试服务器上的版本变化/掉线/权限/挂载替换/凭据与路径边界；双平台与成品独立验收。原型不能算网络连接通过。
- 影响范围：未来 source adapters/services/routes、Tauri 凭据/主机身份、Vue 文件栏、TargetProfile、预览渲染、monitor与投影；页面/监控/平台/发行规则。远程只读投影拟放本机独立 workspace，必须先评审并更新现有成本三件套路径不变量，不能直接把 URI 当 watch_dir。SourceBinding 与各模块准备度详见设计 §12，未归属不得自动计入公司、人工修订另存受保护层；首版不开放远程终端、写回、删除、正式离线导出或多目录同时监控。

<a id="bank-01"></a>

### BANK-01 通用银行对账单版式引擎（无模型，余额链自校验）

- 优先级 / 状态 / 目标版本：P1 / 首批公司表格映射已接入，余项待实施 / 待定
- 已实现（2026-11-17）：B7 CSV/单表 XLSX/可还原文字 PDF，三种金额、顺逆序与双向余额全链验证，按公司保存声明式版式，后续公司账簿/往来重新校验复用，保留 BOC；错误/多解禁存。
- P3 已实现（2026-11-17）：逐文件识别/行数/余额链/页脚状态；无账号列可手填并绑定档案，出现账号列时必须一致；简单整表双金额页脚核对。档案含业务账号，只能私有保存。32个冷文件/5秒，pending刷新继续，超时进程回收。
- 剩余证据与验收：CLI与凭证生成已共用 discover，公司自定义银行目录已回归；OFD、扫描 OCR、复杂多表/小计页脚/账号元数据提取、归一化指纹与通用回单待实现；以合成边界和真实脱敏样本分别验证，不以首笔倒推等同独立期初证明。影响 bank/workpaper/vouchers、公司读取器与页面；未完成前不关闭 BANK-01。
- 问题与证据：各银行的对账单、流水明细、回单版面与术语不同（“借方发生额 / 支出 / 付款金额”，“对方户名 / 收(付)款人名称”等），同一账户的网银导出与柜台打印也不同；现有 `bank/boc.py` 是单一银行的硬编码适配器，换一家银行就要写代码。
- 方案（确定性流水线，不依赖内置模型）：
  1. 取带坐标的文本：PDF / OFD 取文字与坐标，xlsx / csv 直接取单元格；扫描件先经现有 OCR，结果标低置信度。
  2. 版式指纹：银行名关键词 + 归一化表头 + 列数 + 页面尺寸 → 查版式档案库（内置常见银行 + 用户确认过的版式）。命中则直接按档案取列。
  3. 未命中时通用还原：用表头同义词词典给每列打分，按表头词与竖线确定列的横向范围，按基线聚类成行，没有日期 / 金额的续行并入上一行的摘要。再做内容类型检查（日期、金额、账号、空值写法），表头与内容不一致的列交给人工。
  4. 借贷方向由余额链决定：支持双金额列、单金额列加借贷标志、带符号金额三种写法，对每种方向假设逐行验证“上一行余额 ± 本行金额 = 本行余额”，只接受全部成立的那一种；倒序排列同样检验。词典里的“借方”只作候选，因为各银行对借方的站位不一致。
  5. 校验：逐行余额链、页脚本页合计与笔数、上月期末与本月期初连续、日期单调、流水与回单按流水号 + 金额或日期 + 金额 + 方向唯一匹配。任何一项不成立的行标为待人工，不入账、不猜。
  6. 新版式只需人工确认一次列映射，保存为声明式版式档案（指纹 → 列映射、方向规则、日期格式），以后同版式自动识别；当前档案可能含 account_fixed 等业务资料，必须私有保存，不可直接分享。未来可分享模板须显式剥离业务字段并另行设计。
  7. 回单：按标签词典（付款人 / 付款方户名 / 付款账户名称……）与坐标配对标签和值，一页多张时按标题重复切分；户名归一（全半角、括号、空白）后再参与匹配。
- 验收标准：合成的三种借贷写法与正倒序样本都能自动判出方向；故意错一列或缺一个月时，余额链能定位到具体行；同一版式第二次导入无需人工；现有中国银行样本的结果与 `boc.py` 完全一致。
- 关联：未命中版式时，除人工确认列映射外，可由已接入的 Agent 起草版式档案草案、软件校验后供用户确认，见 [AGENT-04](#agent-04)。
- 影响范围：`src/invoice_hub/bank/`（新增通用引擎与版式档案，保留 boc 适配器作为内置档案）、相关测试、BOOKKEEPING 规则；版式档案存放在公司资料夹或私有配置，不进入公开仓库。

- 问题与证据：AGENT-01 只能拉取；Agent 不知道新发票入库、重新汇总完成或成本状态变化，只能轮询。用户也看不到哪个 Agent 正在读写什么。

- 验收标准：合成目录新增一张发票后，已订阅的 Agent 在一次同步完成内收到通知；面板与事件一致；审计不含票面正文。
- 影响范围：事件生产者与 SSE、`common.js`、设置页或新 `/agents` 页、INTERFACES_AND_FLOWS §5、WEB_UI 规则。

### AGENT-04 Agent 辅助导入：识别失败的表格 / PDF 由 Agent 起草版式或纠错

- 优先级 / 状态 / 目标版本：P2 / 待评估 / 待定（依赖 BANK-01、AGENT-01、AGENT-02）
- 问题与证据：2026-11-09 用户提出：用户放入 Excel、PDF 等数据表（对账单、回单等）时，软件未必能识别好；软件能做好最好，做不好时让 Agent 辅助识别并纠错。现有 `bank/` 只有单一银行的硬编码适配器，换版式即失败；BANK-01 的通用引擎对未命中的版式仍需人工确认列映射。
- 方案：软件先识别，成功则不叫 Agent；失败或有低置信列时生成“需要协助”的导入任务。Agent 用只读工具取带坐标的原始提取与失败项，优先提交**版式档案草案**（列映射、方向规则、日期格式），兜底提交**逐格更正**（必须指向原文页码与坐标、写明原值与新值，不得凭空加行）；软件按草案重新解析并跑余额链、合计、笔数、衔接、回单匹配等全部校验，零写入返回结果，Agent 可反复修改；通过后只写导入暂存，用户在页面对照“软件结果 / Agent 结果 / 改动来源”后确认入底稿，版式档案入库，同版式下次由软件自动识别。没有自检结构的表标“未经机器核对”，逐行由用户确认。详见 [Agent 接入设计](AGENT_ACCESS_DESIGN.md) §8。
- 验收标准：合成对账单错一列 / 缺一行时进入“需要协助”；未通过校验的草案不能进暂存；确认前底稿零变化；同版式第二次导入不再需要 Agent；缺坐标的逐格更正被拒；底稿行保留“来源：Agent 更正”；未接入 Agent 时同一任务可由用户手工完成。
- 影响范围：`bank/`（引擎、版式档案、校验）、导入任务与暂存目录、Agent 网关工具、导入页面、BOOKKEEPING 规则、INTERFACES_AND_FLOWS、DATA_AND_ALGORITHMS。

### AGENT-03 Agent 写入：应用内审批与 L1/L2 写工具

- 优先级 / 状态 / 目标版本：P3 / 暂缓 / 待定（2026-11-09 用户决定先只读，AGENT-01 的控制模型用顺手后再评估）
- 问题与证据：客户端自带的工具权限提示可被用户关闭（跳过权限模式），不能作为业务写入的最终关口；写入还必须遵守现有 revision、写锁与手改保护。
- 方案：L1（手改字段、开票参考状态、做账决定、重算、重新汇总）与 L2（单据导出、凭证导出、映射迁移、批量改名、切换活动目录）先零写入预演，进入审批队列，页面卡片显示差异，批准后在写锁内重验 revision 再执行；Agent 侧同步等待，超时返回审批 ID 供查询，不自动重提。真实账套录入、删除、关闭服务、更新安装不开放。审批复用 AGENT-01 的规则与询问卡片，只增加“动作”维度，L2 永远询问；Windows 改用命名管道。详见设计 §4—§6。
- 验收标准：批准前文件零变化；批准后结果与页面同一操作逐字节一致；revision 变化时拒绝；超时后可查到最终状态且无重复写入。
- 影响范围：网关、审批任务、`bookkeeping/`、`projections/`、`services/`、设置页、BOOKKEEPING / WEB_UI / WINDOWS 规则、INTERFACES_AND_FLOWS、DATA_AND_ALGORITHMS（审批任务字段）。

### BUG-01 开票参考销项税率固定 13%、成本固定不含税

- 优先级 / 状态 / 目标版本：P0 / 进行中 / 待定（2026-11-05 在 `codex/cost-output-tax-rate` 实现：按公司设置纳税人类型与销项税率，成本计入不可抵扣税金；全量测试与合成数据页面验收通过；待真实业务目录与 Windows 验收后关闭，见 CHANGELOG 同日小节。品目级税率覆盖随 COST-02 品目表实现）
- 问题与证据：`projections/cost_analysis.py` 的 `REFERENCE_OUTPUT_TAX_RATE = Decimal("0.13")` 用于参考含税价和参考税金；成本基数固定取 `金额(除税)`。2026-11-05 用户确认部分公司是小规模纳税人（3% / 1%），劳务类公司也有 3%、1% 等税率。小规模公司进项不能抵扣，成本应为价税合计；销项按征收率开票。现在这类公司的参考成本偏低、参考含税价按 13% 偏高。一般纳税人取得普票的进项同样不可抵扣，成本也被低估。
- 方案：公司设置增加纳税人类型与默认税率 / 征收率，品目可覆盖；进项税是否计入成本按纳税人类型、票种与抵扣勾选判定；征收率优惠来源于税务工作台政策中心，不写死。详见[成本分析 v2 设计 §4.1、§5](COST_ANALYSIS_V2_DESIGN.md#41-进项税是否计入成本)。
- 验收标准：合成小规模公司（征收率 1%）的参考成本 = 进项价税合计加权，参考含税价 = 参考除税价 × 1.01；一般纳税人专票场景与现在逐行一致；一般纳税人普票进项按价税合计计成本；页面与工作簿标注成本是否含税和所用税率；API 兼容字段不变。
- 影响范围：`projections/cost_analysis.py`（参考价与参考税金）、公司设置、开票参考 sheet、`/costs` 页面、API 契约测试、COST_ANALYSIS 规则与数据算法 §9。
