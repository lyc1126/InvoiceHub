# 税务工作台：价值评估与就绪度

## 2026-11-17 B8 手工基础的假设与停止条件

用户本轮要求继续 P2，授权工作区独立税费记录与手工假设算术接入；不视为政策内容复核签署。当前仅公司期间身份、六税种申报/缴纳记录、普通一般计税四项手工输入与同源 trace。停止条件：缺身份/输入、留抵不符、特殊计税或政策/表式未经复核时不生成自动税务结论。无签署规则包、表式映射和征期，完整 D0—D5 仍待评估；不得用此基础声称正式税务工作台已验收。

> 2026-09-12 · **决策文档，不是设计规格。** 用于在投入开发前重新评估“做不做、先做哪块、以什么形态做”。

> 配套：[交互与架构设计](TAX_WORKBENCH_DESIGN.md)、[算法与政策规格](TAX_ALGORITHMS_AND_POLICY.md)、[政策来源与核验](TAX_POLICY_SOURCES_AND_REVIEW.md)。

## 1. 结论摘要

| 结论 | 依据 |
|---|---|
| 计算器**设计成熟、实现为零** | 设计文档齐备，但仓库内没有生产代码、路由与测试（第 3 节） |
| 旧草稿**不在本工作树可及范围** | 工作树、两个 stash、全部 Git 历史均无其 `.py` 源码（第 3.2 节） |
| 政策中心解决的是**更真实的痛点**，但成本结构是运营型 | 会计痛在“不知变化、不知出处”，而非“算得慢”（第 4 节） |
| 建议先做**最小形态** | 手工测算 + 订阅提示；不读公司资料、不写解读、不覆盖地方口径（第 5 节） |

## 2. 需求侧：会计的痛点

| 痛点 | 现状 | 为什么现有手段没解决 |
|---|---|---|
| 政策多变，不知什么时候变的 | 靠人提醒、靠群消息、靠偶然看到 | 官方源没有面向单个企业的变更通知 |
| 不知出处 | 记不住文号，也定位不到条款 | 检索能查到文件，但查不到“这一条” |
| 有变化但没通知 | 默认没人通知 | 通知能力缺失，且噪音多、与己无关 |
| 官网正文没有解读 | 正文是法律，本就无解读；官方解读散落在解读栏目、答记者问、纳税服务渠道 | 解读不跟条款绑定，也看不出是否仍现行 |
| 解读满天飞，不知谁说了算 | 自媒体、社群、代账同行各说各话 | 缺少“法条 / 官方解读 / 地方口径 / 个人观点”的可信度分层 |

第五项容易被忽略，但它可能是最值钱的：问题不是没有解读，而是**解读与法条混在一起，看不出谁说了算**。这一层正是[政策来源与核验](TAX_POLICY_SOURCES_AND_REVIEW.md)第 2 节要解决的。

## 3. 计算器：就绪度与缺口

### 3.1 现状（可用命令复核）

| 层面 | 事实 |
|---|---|
| 生产代码 | `git ls-files` 无任何 tax 文件；`src/invoice_hub/api/app.py` 无 tax 路由；`tests/` 无 tax 用例 |
| 计算引擎 | 不存在。`src/invoice_hub/tax/` 只剩 `__pycache__`（`engine`/`calculators`/`registry`/`effective_dates`/`errors` 的字节码）与空的 `rules/` |
| 原型 | `docs/design/tax-calculator-prototype.html` 共 297 行，只有 12 处 `Math.`，**没有 `parseFloat`/`toFixed`/`Number()`**：它不进行任何金额运算，只播放预设案例 |
| 设计规格 | 完备：交互、算法、政策治理、申报衔接均有可执行规格 |
| 可复用现成代码 | `services/dossier.py::BusinessDossierService.business_dossier_root` / `_scan_business_dossier` 真实存在，但属于做账资料夹导航，不是计算器 |

结论：**作为会计能用的工具，完成度为零；作为可开工的规格，完成度很高。** “可点击原型”容易让人误判距离，实际差的是全部实现。

### 3.2 旧草稿定位核查

设计文档原先写的是“D0 从最新 main 逐文件迁入可复用 MVP”。核查结果不支持这个前提：

| 核查位置 | 结果 |
|---|---|
| 当前工作树 | 只有 `__pycache__` 与空 `rules/`；源码约在 2026-09-08 被移除 |
| `stash@{0}`、`stash@{1}` | 均不含 tax 路径 |
| 全部 Git 历史 | 无 `src/invoice_hub/tax/` 的新增记录（草稿从未提交，符合其 ignore 状态） |

**源码可能在发布工作树之外的私有归档或原工作区，本轮未核实。** 因此 D0 不得假定“可直接迁入”：应先定位草稿本体只读核对可复用范围；若确认不可得，D0 改为**按算法规格重新实现**，用算法文档第 10 节的独立预期验收，而不是移植既有实现。

### 3.3 三档门槛

| 档位 | 门槛 | 内容 |
|---|---|---|
| **能算** | 手工测算可用 | 生产引擎（`Decimal` 纯函数 + 规则包 + 舍入节点）、规则包按官方原文重建、独立预期值、API 与前端接线、口径自证（用了哪条规则、哪一版、核对到何时） |
| **敢用** | 会计敢拿它对账填表 | 申报表映射、征期与申报期限、留存备查清单、到分舍入与申报表对齐、税费种认定与公司档案、测算/已申报/已缴三栏对照 |
| **进流程** | 长期日常使用 | 测算归档与可复算、与发票成本做账的只读联动、公司资料夹绑定与增量归集 |

其中“**到分舍入与申报表对齐**”是能算与敢用的分界线：没有申报表样例时只能叫“手工测算”，不能声称与申报系统一致，而该样例目前完全没有。

### 3.4 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 草稿丢失 | D0 计划失效 | 先定位；不可得则按规格重写并重做预期值 |
| 无申报表舍入样例 | 无法证明“算得准” | 只输出测算并明确标注未核验，不宣称报税级准确 |
| 适用性判断难以软件化 | 税目是否适用、资格是否成立仍需人判断 | 首轮把“这是手工测算、不是税务结论”写在界面上，而不是只写在文档里 |

## 4. 政策中心：价值与护城河

### 4.1 五个能力与可实现性

| 能力 | 难度 | 判断 |
|---|---|---|
| 变更发现 | 中 | 能做好，但**必须防漏报**（见政策文档 6.2） |
| 溯源（文号、条款、原文链接、生效日） | 低 | 能做得扎实 |
| 关联与提醒（这条和我有关吗） | 中高 | 能做，但**依赖公司档案** |
| 差异与适用性（这版改了什么、对谁生效） | 高 | 部分能做；**不应自己写解读** |
| 可信度分层 | 低 | 能做，且是当前最缺的一层 |

### 4.2 三个关键判断

**一、价值 = 采集 × 关联。** 只把政策收全，用户没有理由不用官方渠道；差别在于**过滤**——不是推 100 条，而是告诉他其中 2 条与他有关。这要求先有公司画像（税费种认定、行业、地区、身份）。**所以政策中心的真正前置不是采集能力，而是公司档案。** 没有它，形态只能停在“可检索的政策库”，价值大打折扣。

**二、不要自己写解读，要的是差异。** 正文是法律，本就不该有解读；官方解读只是散、难找、不跟条款绑定。正确做法是：把散落的官方解读归位到条款、显示新旧版本差异、标注对哪类纳税人适用。前两项是工程，第三项最贵且责任最大，必须由税务内容复核者签署。

**三、护城河是“规则版本 ↔ 政策变更”闭环。** 政策变化产生规则包新版本，所有用旧规则算过的测算自动 `stale`，用户看到“你 3 月算的那笔，适用文号变了”。**掌握用户计算历史的资讯产品才能做到这件事**——这才是把“信息合集”和“计算器”绑成一个产品的理由。

### 4.3 失败模式

1. **做成资讯流**：上线热闹一周，之后没人打开。会计不每天读政策，形态必须是“遇到问题才用”的场景化提示。
2. **解读越界**：一旦自行生成税法结论，错一次就是责任，且用户无法分辨。宁可显示“未核验”。
3. **无人复核**：采集可自动，签署必须由人持续完成。没有固定人力时，功能会在数月内过期并失去信任。

## 5. 最小可用形态

| 版本 | 范围 | 解决什么 | 前置 |
|---|---|---|---|
| **v1** | A 级来源变更提示 + 原文定位 + 覆盖声明；不解读、不碰公司资料 | 不知出处、没有通知 | 无，可独立交付 |
| **v2** | 接公司档案，做“与你有关”过滤 + 场景化待办（征期、生效日、需动作） | 噪音过滤 | D2 公司画像 |
| **v3** | 规则包版本闭环，测算自动 `stale`；官方解读归位到条款 | 变了会影响什么 | D0/D3 规则包 |

计算器侧同理：**先只做第一档“能算”，并明确它只是手工测算工具**。会计日常最高频的需求（“这张 113,000 的合同要不要交印花税”“附加税大概多少”）本就是手工输入条件算的，不需要读公司目录；不碰公司资料也绕开了绑定与归集的大量风险。第二档的价值高度依赖申报表样例与地方口径，两者目前都没有，硬做只会产出“看起来像报税结果”的东西——那比没有更危险。

## 6. 开发者重新评估清单

按仓库既有实验纪律组织：先写假设与停止条件，再看结果。

| 项目 | 内容 |
|---|---|
| **假设** | 会计会为了“知道政策何时变、出处是哪条”而反复使用本功能，且愿意为此维护一份公司档案 |
| **会改变决策的结果** | v1 上线后一个征期内：待办打开率、提示被标记“与我有关/无关”的比例、因覆盖声明而放弃查询的次数 |
| **最小样本** | 一位真实会计 + 一个真实征期 + 5—10 家公司的档案；不需要全量政策覆盖 |
| **停止条件** | 无固定复核人力持续一个月，或 v1 上线两周无人打开，或覆盖声明无法给出可信答案 → 停止扩张，退回“不解读、只提示、只覆盖 A 级源”的最小形态，或不做 |
| **不得执行的实验** | 无法影响上述决策的采集规模试验、以“政策库内容量”作为成功指标、用合成数据证明“会计会用” |

**判断这个功能值不值得做，不取决于能采集多少条政策，而取决于三件事：谁复核、怎么证明没漏、以及能不能把变化关联到具体的一家公司。** 三者缺一，产品形态就应降级。
